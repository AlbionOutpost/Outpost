# Discord sign-in and shared navigation review

The owner reported that Discord sign-in did not work. Anonymous public browser checks on 29 October 2026 reached Discord's login screen, with the registered HTTPS callback, `identify email`, state and S256 PKCE. They did not enter credentials or consent. The owner-only configured OAuth credential pair matched the runtime preparation file; Discord accepted an application-only client-credentials grant, immediately revoked successfully. This validates the supplied pair, not the secret bytes currently deployed or a personal authorization-code exchange.

A concrete startup error was reproduced by intercepting only the browser's local response to `/api/auth/signin/discord` with 503 JSON. The existing NextAuth v4 client ignored the failed status for OAuth, navigated to its fallback and left the visitor on sign-in with no explanation. The replacement button calls the same NextAuth providers, CSRF and sign-in endpoints with a 15-second bound, checks HTTP/JSON failures, validates the Discord authorization destination and required state/PKCE parameters, and shows a pending state or actionable retry. Server NextAuth authorization-code handling, CSRF, state, PKCE, database sessions and owner-admin rules are unchanged.

NextAuth supplies absolute callback URLs on retry. A separate page helper permits only the configured server origin before applying the narrow relative return allowlist. Team invitation confirmation adds only canonical `/invitations/` paths followed by exactly 64 lowercase hexadecimal characters; query parameters, fragments, encoded characters and traversal are rejected. Anonymous invitation sign-in returns to the confirmation page and never accepts the invitation automatically. Expiration, single-use and current membership checks remain in the existing service. Unknown provider error text is never rendered directly.

Public negative checks confirmed that forged state without cookies returns a same-origin OAuthCallback error without issuing a session, and missing CSRF returns the owned sign-in recovery path. Adapter source review found ordinary single-query private RPC operations with the existing Account/Session model relations, not an unsupported interactive transaction.

The shared header now renders text-only primary links on every route, including sign-in/legal; the previous product-only SVG hiding rule caused different visible links. Teams retains the existing `/groups` destination. More uses the shared Shell structure and marks account destinations active. Native banner SVG/ICO/Apple icons use Next's metadata file conventions; layout behavior is unchanged.

Evidence: sanitized public probes in `.qa/signin-audit/public-start.json`, `public-provider.json`, `credential-check.json`, `public-negative.json` and `public-start-failure-before.json`. 80 focused unit cases pass across `tests/discord-sign-in.test.ts` and `tests/build-composition.test.ts`; typecheck and affected ESLint pass. `e2e/signin-navigation.spec.ts` covers startup failure/retry, approved returns, forged callbacks, safe errors, shared navigation and actual icon responses. The existing group invitation journey additionally checks anonymous return links, already-authenticated absolute callback retries and unchanged membership until explicit acceptance. Coordinated runtime results are recorded by the parent phase gate.

Personal Discord consent, genuine token exchange, session persistence and real owner-admin assignment remain unverified. The changes do not claim to have reproduced or repaired an unobserved end-to-end provider/account failure. No token, cookie value, client secret or private response body is included in these artifacts.
