# HTTP API

All routes live under `src/app/api`. JSON in and out. Mutations (`POST`/`PUT`/`PATCH`/`DELETE` on private data) go through `mutationUser`: same-origin `Origin`, a session, and the `content:<userId>` budgets (30/min and 600/day). Build and comp saves also spend a daily byte budget and are bounded per account (see **Storage limits** under Builds). Private JSON bodies must be `application/json` (64 KiB default, 1 MiB for comps). Authentication POST bodies are byte-bounded at 64 KiB before dependency parsing; Stripe webhooks at 256 KiB before signature parsing. Errors are `{ error }` with non-disclosing messages; private responses are `Cache-Control: private, no-store`.

**Auth:** pub = public · sess = requires session · owner/member = checked against current DB rows.

**Limits.** Cloudflare requests require the platform-provided client address: 240 requests/minute per address (IPv6 counted per /64, so rotating through one allocation does not renew any per-address budget) precede render routing and cache hits, and price/history routes share a 20/minute per-address/server request budget (the item database's `/api/items/prices` has its own 20/minute per-address/server allowance, so paging through items never spends it). `/api/search` answers that miss the edge cache (another query, or a session cookie) take 30/minute per address, because each one scans builds, comps and Teams in the single private store. Every actual AODP attempt (including retries and fanout, after cache hits) additionally reserves one of 10/minute per-address/server slots before the shared 50/minute and 250/five-minute regional budgets. Client cookies and forwarded-for headers cannot renew these allowances. Public caller-supplied price IDs must occur in the supported source catalog; that is not current-patch verification. Authentication is 40/minute per trusted Cloudflare address with a 2,400/minute site-wide backstop. Node does not trust arbitrary proxy headers and uses only the larger auth backstop; publicly hosted Node operators must supply appropriate trusted-proxy/edge abuse controls. Signed-in mutations remain 30/minute and 600/day per user, exports 5/hour, settings 20/minute. Distributed callers can still exhaust finite shared provider capacity; unavailable/stale observations are not substituted with invented prices.

**Storage limits** (`src/lib/storage-limits.ts`). One account keeps at most 500 builds and 500 comps (Team comps count against the member who created them); creating or copying one more is 409 and writes nothing, while edits of existing ones still save. Each build and comp keeps its last 50 revisions: the save that adds revision _n_ deletes revision _n_ − 50 and older in the same transaction (`createBuild`, `reviseBuild`, `duplicateBuild`, `saveComposition`). Every create, edit, restore and copy also spends the `content-bytes:<userId>` budget of 50 MiB a day, counted in KiB of the saved JSON (a copy counts at its type's largest body: 64 KiB for a build, 1 MiB for a comp); a save that does not fit is 429 before anything is written and spends nothing. The editors show the server's message.

**Team roles.** Every action re-reads the actor's roles inside its transaction. `manageGiveaways` (bit 1024) starts, edits, cancels and draws the Team's giveaways; it went to every role that held `manageTeam`. Rights are the union of the permissions of the roles a member holds; the owner has all of them. Permissions (`teamPermissions` in `src/lib/groups/permissions.ts`): `manageTeam` (profile, crest and the guild tax: `profile` takes an optional `guildTaxPercent`, and `guild-tax` sets only `guildTaxPercent`, 0–100 with one decimal, 400 otherwise; with `manageComps`, delete anyone's Team comp), `manageRoles`, `inviteMembers` (create links, revoke your own), `manageRequests` (decide requests, revoke any link), `removeMembers`, `manageEvents` (events, cancelling, announcements), `manageComps`, `manageLoot`, `manageBuilds` (share and remove builds). RSVP, leave and reading Team content need only membership; `transfer` and `delete` are owner only. Missing permission is 403; an outsider gets 404.

`remove` needs `removeMembers` and a target whose highest role is below the actor's. `transfer` gives the previous owner the Team's highest role. Open invitation links whose issuer no longer holds `inviteMembers` are revoked after any role change, and accepting a link re-checks the issuer. The old `role` action is gone (400).

**Team profile** (`action: "profile"`, `manageTeam`, same transaction as every Team mutation): `name`, `description`, `region`, `visibility`, `expectedUpdatedAt`, plus `crestItem` (one of the 40 crest symbols in `src/lib/groups/crest.ts`, or null for the default), `crestColor` (`ember`, `gold`, `crimson`, `forest`, `teal`, `azure`, `violet`, `steel` or `null`), `activities` (up to three distinct build activities, `Other` excluded) and `recruiting` (boolean). Anything else is a 400; members without `manageTeam` get 403, outsiders 404. Omitted identity fields reset to the monogram, no activities and recruiting. A `request` to a public Team that is not recruiting is a 409 and queues nothing. No uploads: a crest is never an image a player sends.

## Older personal records

Timer and saved-scenario GET responses retain their array bodies. Timers return up to 100 rows and scenarios up to 50 (optionally filtered by kind). When another page exists, the response supplies `X-Next-Cursor`; pass that value as the `cursor` query parameter using `URLSearchParams`. Ordering is descending update time with ID as a stable tie-breaker. The cursor contains ordering information only: every page still requires the current session and applies the same owner/kind filters. Malformed or oversized cursors return 400. Deleting the boundary record does not invalidate a cursor. Reload to see records updated above the current boundary.

The timers page, calculator saved scenarios, transport plans and shopping account lists expose explicit controls to load older entries. Existing records remain stored; there is no silent creation cap or replacement of older saves.

## Account saves

Library build favorites and specialization levels live on the account when signed in and in the browser for guests (`src/app/api/account/saves/route.ts`, service `accountSaves`).

`GET /api/account/saves` (session, else 401; `private, no-store`) answers `{ favorites, unavailable, limit, levels }`: the account's library favorites newest first, each resolved on the server to its library summary (`id`, `slug`, `title`, `author`, `weaponName`, `category`, `itemId`, `updatedAt`), `unavailable` saved builds no longer in the library, `limit` 100, and `levels` as `{ specId: 1–100 }`. Only the session's own rows are read.

`POST /api/account/saves` goes through `mutationUser` (exact Origin, session, content budget) with a strict JSON body (128 KiB) of one of:

- `{ "action": "favorite", "slug", "active" }` → `{ favorite, total }`. Saving resolves the slug against the library first (unknown → 404); 100 per account (409 beyond). Removing never needs the build to still exist.
- `{ "action": "levels", "levels": { specId: 0–100 } }` → `{ levels }`. Replaces the account's levels; 0 drops a spec; at most 400 specs; ids `[a-z0-9_]{1,80}`.
- `{ "action": "merge", "favorites": [slug…≤300], "levels" }` → the GET answer plus `skipped`. Merges a browser's copy: adds library builds the account lacks (unknown ones are dropped, up to 100 in all) and keeps the higher level per spec. Merging the same copy again changes nothing.

Any `userId` or other extra field is 400; cross-origin 403; signed out 401. The browser merges its copy once after sign-in and remembers what it sent (`outpost:account-merged:v1:<userId>`), so a favorite removed on the account is not added back, while one saved later as a guest still moves over. Rows (`LibraryFavorite`, `MasteryLevel`) are in the account export and go with the account on deletion.

## Account likes for public library entries

`GET /api/library-likes?items=build:slug,composition:slug` reads up to ten distinct entries in one request (one session lookup, one database round trip): `{ signedIn, items }`, with `items` keyed by each `kind:slug` as asked and each entry `{ found: true, archivedCount, outpostCount, count, liked }` or `{ found: false }`. Malformed, repeated or more than ten entries return 400. Per account: `Cache-Control: private, no-store`, never edge cached. The homepage like chips share it.

`GET /api/library-likes/{kind}/{slug}` accepts `kind=build|composition`. It reads an existing public snapshot, returning `archivedCount`, `outpostCount`, their combined `count`, the current account's `liked` flag and `signedIn`. Responses use `Cache-Control: private, no-store`; no voter identities are returned. Build IDs and slugs canonicalize to the snapshot slug before counting or writing.

`POST` to the same route requires a current server session, matching Origin and JSON body `{ "active": true }` (or false to remove the caller's like). The body is strictly bounded to 1KiB and accepts no actor/count fields. Existing per-account mutation quotas apply. Unknown entries return 404; anonymous/expired sessions 401; cross-origin requests 403; invalid/extra fields 400. A unique account/kind/canonical-slug identity plus bounded serializable conflict retries makes repeated writes idempotent.

The new `LibraryLike` rows are private account records with public aggregate counts. They do not rewrite imported archive votes or existing device favourites. Account export includes only the account's own rows; deleting the account cascades them. PostgreSQL migration `20261102210000_library_likes` and additive SQLite migration `0007_library_likes.sql` add the store. The private Worker upgrades schema 5 to 6. A web rollback can retain schema 6; an older schema 5 backend needs compatibility or a roll-forward plan. No production migration is implied by this API documentation.

| `POST /api/admin/bans`                      | Strict ban/unban, Discord ID, version, reason, 7/30/0 days and exact typed confirmation                         |

Zero days means until revoked.409 indicates a stale revision/version and requires reloading. Owner/ADMIN ban protection returns 403; protected session revocation returns 400. Unknown users 404. Additional overview/review/audit reads are named private database services invoked by server pages, not public analytics endpoints.
