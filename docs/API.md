# HTTP API

All routes live under `src/app/api`. JSON in and out. Mutations (`POST`/`PUT`/`PATCH`/`DELETE` on private data) go through `mutationUser`: same-origin `Origin`, a session, and the `content:<userId>` budgets (30/min and 600/day). Private JSON bodies must be `application/json` (64 KiB default, 1 MiB for comps). Authentication POST bodies are byte-bounded at 64 KiB before dependency parsing; Stripe webhooks at 256 KiB before signature parsing. Errors are `{ error }` with non-disclosing messages; private responses are `Cache-Control: private, no-store`.

**Auth:** pub = public · sess = requires session · owner/member = checked against current DB rows.

**Limits.** Cloudflare requests require the platform-provided client address: 240 requests/minute per address (IPv6 counted per /64, so rotating through one allocation does not renew any per-address budget) precede render routing and cache hits, and price/history routes share a 20/minute per-address/server request budget. Every actual AODP attempt (including retries and fanout, after cache hits) additionally reserves one of 10/minute per-address/server slots before the shared 50/minute and 250/five-minute regional budgets. Client cookies and forwarded-for headers cannot renew these allowances. Public caller-supplied price IDs must occur in the supported source catalog; that is not current-patch verification. Authentication is 40/minute per trusted Cloudflare address with a 2,400/minute site-wide backstop. Node does not trust arbitrary proxy headers and uses only the larger auth backstop; publicly hosted Node operators must supply appropriate trusted-proxy/edge abuse controls. Signed-in mutations remain 30/minute and 600/day per user, exports 5/hour, settings 20/minute. Distributed callers can still exhaust finite shared provider capacity; unavailable/stale observations are not substituted with invented prices.

**Team roles.** Every action re-reads the actor's roles inside its transaction. Rights are the union of the permissions of the roles a member holds; the owner has all of them. Permissions (`teamPermissions` in `src/lib/groups/permissions.ts`): `manageTeam` (profile and crest; with `manageComps`, delete anyone's Team comp), `manageRoles`, `inviteMembers` (create links, revoke your own), `manageRequests` (decide requests, revoke any link), `removeMembers`, `manageEvents` (events, cancelling, announcements), `manageComps`, `manageLoot`, `manageBuilds` (share and remove builds). RSVP, leave and reading Team content need only membership; `transfer` and `delete` are owner only. Missing permission is 403; an outsider gets 404.

| Action         | Body                                                                                                              | Rules                                                                                                                                          |
| -------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `role-create`  | `name` (1–32), `color` (`muted`, `ember`, `gold`, `green`, `teal`, `blue`, `violet`, `red`), `permissions` (keys) | `manageRoles`; placed at the bottom; at most 25 roles (409); only permissions the actor holds (403)                                            |
| `role-update`  | `roleId`, `name`, `color`, `permissions`                                                                          | `manageRoles`; role strictly below the actor's highest role; may only add or remove permissions the actor holds                                |
| `role-delete`  | `roleId`                                                                                                          | `manageRoles`; below the actor; the default role is a 409 until another role is the default                                                    |
| `role-move`    | `roleId`, `direction` (`up`/`down`)                                                                               | `manageRoles`; swaps with the neighbour; both must be below the actor; 409 at the end                                                          |
| `role-default` | `roleId`                                                                                                          | `manageRoles`; below the actor; new members (approved requests, accepted invitations) get this role                                            |
| `member-roles` | `userId`, `roleIds` (the full set, up to 25)                                                                      | `manageRoles`; the target must rank below the actor (or be the actor), never the owner; every role added or taken away must be below the actor |

`remove` needs `removeMembers` and a target whose highest role is below the actor's. `transfer` gives the previous owner the Team's highest role. Open invitation links whose issuer no longer holds `inviteMembers` are revoked after any role change, and accepting a link re-checks the issuer. The old `role` action is gone (400).

**Team profile** (`action: "profile"`, `manageTeam`, same transaction as every Team mutation): `name`, `description`, `region`, `visibility`, `expectedUpdatedAt`, plus `crestItem` (one of the 40 crest symbols in `src/lib/groups/crest.ts`, or null for the default), `crestColor` (`ember`, `gold`, `crimson`, `forest`, `teal`, `azure`, `violet`, `steel` or `null`), `activities` (up to three distinct build activities, `Other` excluded) and `recruiting` (boolean). Anything else is a 400; members without `manageTeam` get 403, outsiders 404. Omitted identity fields reset to the monogram, no activities and recruiting. A `request` to a public Team that is not recruiting is a 409 and queues nothing. No uploads: a crest is never an image a player sends.

## Older personal records

Timer and saved-scenario GET responses retain their array bodies. Timers return up to 100 rows and scenarios up to 50 (optionally filtered by kind). When another page exists, the response supplies `X-Next-Cursor`; pass that value as the `cursor` query parameter using `URLSearchParams`. Ordering is descending update time with ID as a stable tie-breaker. The cursor contains ordering information only: every page still requires the current session and applies the same owner/kind filters. Malformed or oversized cursors return 400. Deleting the boundary record does not invalidate a cursor. Reload to see records updated above the current boundary.

The timers page, calculator saved scenarios, transport plans and shopping account lists expose explicit controls to load older entries. Existing records remain stored; there is no silent creation cap or replacement of older saves.

## Account likes for public library entries

`GET /api/library-likes?items=build:slug,composition:slug` reads up to ten distinct entries in one request (one session lookup, one database round trip): `{ signedIn, items }`, with `items` keyed by each `kind:slug` as asked and each entry `{ found: true, archivedCount, outpostCount, count, liked }` or `{ found: false }`. Malformed, repeated or more than ten entries return 400. Per account: `Cache-Control: private, no-store`, never edge cached. The homepage like chips share it.

`GET /api/library-likes/{kind}/{slug}` accepts `kind=build|composition`. It reads an existing public snapshot, returning `archivedCount`, `outpostCount`, their combined `count`, the current account's `liked` flag and `signedIn`. Responses use `Cache-Control: private, no-store`; no voter identities are returned. Build IDs and slugs canonicalize to the snapshot slug before counting or writing.

`POST` to the same route requires a current server session, matching Origin and JSON body `{ "active": true }` (or false to remove the caller's like). The body is strictly bounded to 1KiB and accepts no actor/count fields. Existing per-account mutation quotas apply. Unknown entries return 404; anonymous/expired sessions 401; cross-origin requests 403; invalid/extra fields 400. A unique account/kind/canonical-slug identity plus bounded serializable conflict retries makes repeated writes idempotent.

The new `LibraryLike` rows are private account records with public aggregate counts. They do not rewrite imported archive votes or existing device favourites. Account export includes only the account's own rows; deleting the account cascades them. PostgreSQL migration `20261102210000_library_likes` and additive SQLite migration `0007_library_likes.sql` add the store. The private Worker upgrades schema 5 to 6. A web rollback can retain schema 6; an older schema 5 backend needs compatibility or a roll-forward plan. No production migration is implied by this API documentation.

## Account administration

All routes below require a current global ADMIN. Anonymous/expired sessions return 401; ordinary users and MODERATOR return 403. Reads and writes are private/no-store. POST uses exact Origin, the existing per-user mutation quota, 8KiB JSON and strict validation; current ADMIN is checked again inside the transaction. No role assignment or billing cancellation API is exposed.

| Route                                       | Purpose                                                                                                         |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `GET /api/admin/users?q=&filter=all&page=1` | Search/paginate selected user records, 20/page; filter all/supporters/review/banned                             |
| `GET /api/admin/users/[id]`                 | Selected account details, current ban, open report count, latest 20 relevant administrative actions             |
| `POST /api/admin/users/[id]`                | Strict grant/revoke-gift/revoke-sessions action, reason and `expectedUpdatedAt`; grant accepts 30/90/365/0 days |
| `GET /api/admin/bans?discordId=`            | Current persistent ban/version for a 17–20 digit Discord ID                                                     |
| `POST /api/admin/bans`                      | Strict ban/unban, Discord ID, version, reason, 7/30/0 days and exact typed confirmation                         |

Zero days means until revoked.409 indicates a stale revision/version and requires reloading. Owner/ADMIN ban protection returns 403; protected session revocation returns 400. Unknown users 404. Additional overview/review/audit reads are named private database services invoked by server pages, not public analytics endpoints. Full semantics, privacy and migration limits: [Administration](ADMINISTRATION.md).
