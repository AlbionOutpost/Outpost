# Outpost calculators

Verify the declared accounting model and the game's mechanics independently. Read [DATA_SOURCES](../../../DATA_SOURCES.md), [parity](../../../docs/engineering/CALCULATOR_PARITY.md), [product workflow specification](../../../docs/PRODUCT_UI_WORKFLOWS.md), the relevant modules/tests and [formula protocol](references/formula-protocol.md). Follow the [shared execution contract](../../../docs/engineering/SKILL_SYSTEM.md).

## Workflow

1. Trace UI inputs → schema/defaults → recipe/mechanics → price identity → engine → display/persistence. Start with [production](../../../src/lib/albion/production.ts), [recipes](../../../src/lib/albion/recipes.ts), [trade](../../../src/lib/albion/calculations.ts) or [transport](../../../src/lib/albion/transport.ts). Identify the selected calculator's supported scope before applying mechanics.
2. Create/update the formula ledger: units, quantities, source/revision/patch, assumptions, order execution, rounding, applicable caps and excluded mechanics. Read public Albion Online Grind pages only for workflow comparison when relevant and accessible; record access/URL. Never copy proprietary implementation or infer coefficients from its output.
3. Verify applicable recipes/materials, return eligibility, focus/spec/city bonuses, tax/setup fees and buy/sell order bases using outpost-albion-data. Unknown current coefficients stay manual/unavailable. Do not apply irrelevant mechanics to every engine or claim automatic focus/spec from a manual percentage.
4. Compute independent expected values by hand/rational arithmetic before running production code. Separate upfront cash, retained-resource value, effective cost, gross revenue, net cash/economic profit, ROI, margin, total profit/focus and incremental focus benefit. Document denominators and zero cases.
5. Preserve missing/stale price status and region/city/item/quality/side/timestamp identity. Missing source observations never become zero; an intentional manual zero is a separate supported input. Retain manual overrides across refresh, and visibly label them. Saved assumptions do not make old observations fresh.
6. Run focused tests from the protocol and affected browser journeys. For a change, compare independent expectations to actual results, fix discrepancies and rerun. Verify saved scenario ownership/reload via security when persistence changes. Inspect responsive results using frontend + visual QA.

## Acceptance

Every changed formula has documented units/assumptions/source or explicit unknown status, independent expected-value tests and bounded precision/invalid-input handling. Verify normal and negative profit, zero values/denominators, invalid/fractional quantities, large/overflow values, missing/stale/incorrect-identity prices, region switching, applicable focus/city settings, save/reload and mobile behavior. Record unsupported cases instead of claiming full calculator completion.

Use Playwright MCP for inputs/refresh/region/save interactions after discovering its schemas and confirming success; DevTools only for diagnosed network/console issues. Formula verification uses executable independent fixtures, not browser appearance. Follow the shared fallback policy and mandatory phase QA.

## Prohibited shortcuts and report

No expected outputs generated by the function under test; no invented recipes/rates; no stale/manual/fixture values labelled live; no mathematically plausible result accepted without game-source scope. Do not silently remove fees or use returns to understate initial purchasing cash.

Report **calculator/version/scope → formula and source ledger → independent scenario with units/expected/actual/tolerance → commands/results → UI/source/persistence states inspected → mechanical unknowns and missing workflow → next validation**. Update parity/provenance when actual evidence changes. Distinguish accounting correctness from recipe/current-patch correctness.
